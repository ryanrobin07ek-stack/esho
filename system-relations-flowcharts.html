01 / MAP

Whole-system relationship map

Solid arrows show local or online request relationships; dashed arrows are internet-dependent sync. POS and Studio share the owner device database. A customer browser is separate and reaches cloud services over the internet.

Cloudflare is not a direct database connection from the app. The Worker validates and routes requests; D1 is reached by the Worker. Offline owner-device sales stay local until synchronization.

02 / APP

App surfaces and persistence

The app has multiple screens and runtime shells, but local POS and Studio features converge on one database interface. Separate installations do not share SQLite automatically.

Browser and Android SQLite stores belong to their own device/profile. The public visitor storefront is not the owner app and cannot see its private database.

03 / DATA

Database entities and their relationships

The key is not product name: shared sellable stock is scoped by tenant and exact SKU. POS receipts produce unique events; the queue transports those events without applying them twice.

Simplified logical relations, not a complete SQL schema. The Studio snapshot engine stores JSON payload rows; POS operational and shared inventory tables are normalized SQLite tables on the same local database connection.

04 / LINK

Connecting POS products to website products

Connection is deliberate: select a shop, match by SKU, choose which catalog supplies the initial quantity, then save a local shared balance. A mismatch must not be silently merged.

The initial stock-source choice is a deliberate replacement, not an additive merge. Once connected, both local sales surfaces should read and change the shared balance.

05 / POS

Owner-device POS sale: local first, sync later

The receipt is a local business record. Internet delivery is a later operation; a remote failure must not erase a committed local receipt.

A linked-sale stock trigger checks and decrements the local shared ledger inside the checkout transaction. If the check fails, receipt and stock changes roll back together. A sync conflict later is reported without deleting the receipt.

06 / WEB

Public storefront sale: online Worker transaction

The visitor is on a different device. The request is validated by the Worker and remote shared stock is handled in D1; it cannot directly update the owner phone’s SQLite.

A catalog may render from a saved browser cache, but a public sale still requires internet. A failed stock check must not appear as a successful order.

07 / SYNC

Offline queue, reconnect, retry, and reconciliation

Offline means local work continues and cloud-bound changes wait in durable state. Delivery is retried with the same event identity; acknowledged events are not deducted twice.

If the server commits but its response is lost, the phone retries the same ID. D1 recognizes the existing event; no duplicate stock deduction occurs. If remote stock is insufficient, keep the receipt and expose an explicit reconciliation conflict.

08 / CATALOG

Editing and publishing a website catalog

Editing can be local and retained when offline. Publishing is a cloud action and should only report success after the Worker accepts and stores the cleaned catalog.

The public catalog and private owner/admin payloads have different visibility. Do not put account tokens, master credentials, or private catalog fields into visitor responses.

09 / BOUNDARIES

Trust zones and connection constraints

Each box is a different storage/security boundary. Arrows cross the network only through the Worker API; public visitors must never receive owner-only credentials or private data.

Owner device

Local POS and Studio data. Protect device access and owner sessions. Locally saved sales may be pending for remote sync.

Customer browser

Public catalog, browser-scoped cache, and checkout input. It is not trusted to set authoritative stock or access private owner data.

Worker + D1

Worker validates tenant, authorization, event IDs, quantities, and payloads. D1 stores remote catalog and inventory records.
