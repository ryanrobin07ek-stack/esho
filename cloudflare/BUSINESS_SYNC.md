# Business archive, branch sync, and push setup

The app keeps SQLite as its offline-first source. Archive sync is an explicit, owner-authorized upload from **More → Stores**; it does not delete or replace local records. **Refresh branches** downloads the tenant's latest snapshots and uses them for cross-register dashboard totals on this device. The Worker stores immutable, tenant/register-scoped JSON snapshots in R2 and an index of the latest snapshot per register in D1. A snapshot includes sales, expenses, products, categories, website visits/events, newsletter subscribers, loyalty points, booking holds, register instances, settings, suppliers, purchase orders, and parked POS tickets. Snapshots can contain customer contact details and newsletter addresses, so only sync to an account you control. The Worker returns them only to that tenant's owner and accepts snapshots up to 8 MB.

Live POS cloud backup and sync is separate from archive snapshots. Enable it from **POS → More → Settings** on each device, using the same shop tenant and owner authorization. On first enable, or if initial seeding was interrupted, the register saves its POS products (including current stock), categories, expenses, settings, and sales to its local sync queue and uploads them in batches. Existing POS products without a SKU are assigned and saved a unique generated SKU automatically during seeding; no manual SKU entry is needed to back them up. Subsequent edits, including stock changes after sales and purchase receipts, are queued locally; the app does not make a Cloudflare request for every local edit or sale. Queued changes are retried when connectivity returns, and each device tracks its own revision cursor. Customer/supplier records and receipt data are sent to Cloudflare when enabled. The POS inventory is separate from the customer-facing website catalogue.

The standalone browser register page (`/register`, `register.html`) was removed. POS also runs in the browser build of the app at `/pos`, using SQLite compiled to WebAssembly with IndexedDB persistence; it connects to a shop the same way the Android app does (sign in with the account that owns the shop, or use the shop's private owner key, then enable cloud backup and sync in **POS → More → Settings**). Account sessions are authorized only for tenant IDs linked to or owned by that account. The browser build has no native camera/OCR integrations. `src/browser-register.js` is an unused leftover.

For nearby registers, use **POS → More → Settings → Nearby device sync**. There are two ways to pair. On Android, one phone taps **Receive over Bluetooth** and the other taps **Find a Bluetooth register**. For Wi-Fi, the PC taps **Create pairing QR**, the phone taps **Scan pairing QR** and scans it once, and the PC then asks you to approve the phone before any POS data is sent. The offer and answer are exchanged through a temporary relay (`/api/nearby/pairing`, 180-second expiry), so the internet is needed briefly during setup. After that the POS transfer uses a WebRTC data channel without STUN/TURN relays, directly over the same Wi-Fi and DTLS-encrypted. Pairing data is temporary and the QR should only be shown to a trusted register. Nearby sync merges shop-scoped POS records and queues received changes for normal Cloudflare sync. It does not provide device management or sync while the app is closed. When registers are apart, enable Cloudflare business sync for the same shop; changes remain local first and are uploaded in batches when online.

QR/barcode scanning during product entry is optional and runs locally in the app; it reads the code as a product SKU and does not use machine learning or upload camera images.

Storefront checkout creates tenant-scoped orders that the Worker prices itself from the published catalogue (including options, the shop's delivery fee and free-delivery threshold, and any discount code). The published Litrus storefront (`public/litrus-mixer/live-catalog.js`) posts the order to `POST /api/orders`, then either starts hosted Paystack checkout through `POST /api/payments/paystack/initialize` (customer card or mobile-money details are entered only on Paystack) or leaves the order for the shop to settle (`payment_method: "manual"`), which the owner marks paid in Craft. The storefront verifies a Paystack reference through `GET /api/payments/paystack/verify` and shows payment status from the server response. Orders need migration `0008_storefront_orders.sql` and `0010_storefront_order_payments.sql`; the later commerce features need `0025` to `0029` (see `cloudflare/STOREFRONT_COMMERCE.md`).

Owners connect Paystack under **Studio → Payments**; that requires migration `0009_paystack_subaccounts.sql` (and the later Paystack migrations) and one Paystack **secret API key** stored as the `PAYSTACK_SECRET_KEY` Worker secret. The generic supported-bank directory is read-only and does not require shop-owner authorization; reading or changing a shop’s subaccount still requires owner authorization. There is no Paystack public key or separate webhook signing key to put in the app. Use a Paystack test secret for test transactions and switch the Worker secret to the live secret only for production. Bank and business details are sent to Paystack for setup but are not retained by E-Shop; D1 stores only the Paystack subaccount reference, connection state, bank name, and account last four digits. Subaccounts use zero E-Shop percentage share; transactions explicitly route Paystack processing fees to the shop’s subaccount, with no E-Shop transaction charge. Checkout initializes transactions server-side, uses Paystack-hosted authorization, and marks orders paid only after a matching Paystack verification or signed `charge.success` webhook, or when the owner records a manual payment. Online payment requires positive KES orders and a connected subaccount; storefronts with another currency must not take Paystack payments until their catalogue currency and prices are intentionally configured for KES.

Stock is checked when an order is received but is deducted only when the payment is recorded (once per order and SKU); an unpaid order does not reserve stock, so two customers can still both order the last unit. If stock ran short by the time the second payment arrives, the order is still recorded as paid and flagged `needs_attention` for the owner. Holds are the only reservation mechanism.

Storefront visits can be sent anonymously to `POST /api/analytics/visit`; the owner reads tenant aggregates from `GET /api/analytics/visit?days=<1-365>` (owner key, owner session or admin key). Per-product event counters, including the funnel events `checkout_start`, `purchase` and `booking_submitted`, go through `POST /api/analytics/events`. The Worker records a hash of the random visitor identifier and coarse Cloudflare country/region metadata, not visitor IP addresses. It strips query strings and fragments from paths and retains only the referrer origin. Shared analytics requires its D1 migrations (`0007`, `0018`, `0022`, `0029`) and is separate from each device's locally stored visit history.

To provision a Cloudflare environment:

1. Create the archive bucket: `npx wrangler r2 bucket create eshop-business-archive`
2. Apply the D1 schema: every file in `cloudflare/migrations/` (`0001` to `0030`) in order. As of this writing `0025` to `0030` (rate limits and owner notifications, manual payments and needs-attention flags, discount codes, payment attempts, funnel events, service booking management) have NOT been applied to production. Apply migrations before deploying the Worker code that uses them: `npm run cf:d1:migrate:remote`
3. Generate a VAPID key pair locally with Node:

   ```sh
   node -e "const c=require('node:crypto');const k=c.generateKeyPairSync('ec',{namedCurve:'prime256v1'});const p=k.publicKey.export({format:'jwk'});const s=k.privateKey.export({format:'jwk'});console.log(JSON.stringify({publicKey:Buffer.from([4,...Buffer.from(p.x,'base64url'),...Buffer.from(p.y,'base64url')]).toString('base64url'),privateKey:s.d}))"
   ```

4. Put the generated `publicKey` in `VAPID_PUBLIC_KEY` in `wrangler.jsonc`. Keep `privateKey` out of source control and add it as a Worker secret: `npx wrangler secret put VAPID_PRIVATE_KEY --config cloudflare/wrangler.jsonc`. `VAPID_SUBJECT` is a contact address and can be changed in the config.
5. Add the Paystack secret key as a Worker secret; never put it in app code or `wrangler.jsonc`: `npx wrangler secret put PAYSTACK_SECRET_KEY --config cloudflare/wrangler.jsonc`.
6. Set the Paystack webhook URL in the Paystack dashboard to the production Worker's `/api/payments/paystack/webhook` URL (the Worker is named `eshop-storefront`; use its workers.dev or `rrobin.co.ke` address) and enable the `charge.success` event.
7. Optional email: set `RESEND_API_KEY` as a Worker secret (and `EMAIL_FROM` in `wrangler.jsonc`) for owner alerts, newsletters and account recovery. `RATE_LIMIT_SALT` is an optional secret used to salt the rate-limit IP hashes (it falls back to `PUBLISH_TOKEN`).
8. Deploy the Worker and assets: `npm run cf:deploy`. Deploying (and remote migrations) is a manual, owner-run step; never script it into CI or let an automated agent run it.

Push is Web Push for supported HTTPS browsers. Visitors must separately grant notification permission; newsletter sign-up alone does not opt them into push. Broadcasts require the shop owner key and VAPID configuration. Expired subscriptions are removed, and send counts (not subscription endpoints) are archived in R2. Capacitor webviews that do not implement `PushManager` will report that push is unsupported.

`POST /api/inventory/sale` (the register's shared-stock sale sync) requires the shop owner key, the owner's account session or the admin key; anonymous sales are rejected. Owner alerts, manual payments, discount codes, rate limits, shop deletion and data retention are described in `cloudflare/STOREFRONT_COMMERCE.md`. The `push_subscriptions` table is the customer-facing newsletter list and is never used for owner alerts.

If any provisioning step is skipped, the relevant API returns a configuration error; the local business data remains available.
