# Business archive, branch sync, and push setup

The app keeps SQLite as its offline-first source. Archive sync is an explicit, owner-authorized upload from **More → Stores**; it does not delete or replace local records. **Refresh branches** downloads the tenant's latest snapshots and uses them for cross-register dashboard totals on this device. The Worker stores immutable, tenant/register-scoped JSON snapshots in R2 and an index of the latest snapshot per register in D1. A snapshot includes sales, expenses, products, categories, website visits/events, newsletter subscribers, loyalty points, booking holds, register instances, settings, suppliers, purchase orders, and parked POS tickets. Snapshots can contain customer contact details and newsletter addresses, so only sync to an account you control. The Worker returns them only to that tenant's owner and accepts snapshots up to 8 MB.

Live POS cloud backup and sync is separate from archive snapshots. Enable it from **POS → More → Settings** on each device, using the same shop tenant and owner authorization. On first enable, or if initial seeding was interrupted, the register saves its POS products (including current stock), categories, expenses, settings, and sales to its local sync queue and uploads them in batches. Existing POS products without a SKU are assigned and saved a unique generated SKU automatically during seeding; no manual SKU entry is needed to back them up. Subsequent edits, including stock changes after sales and purchase receipts, are queued locally; the app does not make a Cloudflare request for every local edit or sale. Queued changes are retried when connectivity returns, and each device tracks its own revision cursor. Customer/supplier records and receipt data are sent to Cloudflare when enabled. The POS inventory is separate from the customer-facing website catalogue.

The separate browser register at `/register` is an additional browser-only POS entry point; the primary register remains the app. It uses SQLite compiled to WebAssembly and IndexedDB persistence, without loading Capacitor. Connect it to the same shop using the E-Shop account that owns the shop, or enter that shop's private owner key; then enable cloud backup and sync in **POS → More → Settings**. Account sessions are authorized only for tenant IDs linked to or owned by that account; owner-key authorization remains available. The account password is used only for sign-in and is not saved. The connection token can optionally be remembered in that browser profile; use this only on a trusted computer. Each device keeps its own local data and exchanges queued records through the tenant-authorized Worker endpoint. The browser edition does not include native camera/OCR integrations.

For nearby registers, use **POS → More → Settings → Nearby device sync**. Keep both devices on the same Wi-Fi: one creates a temporary pairing QR and the other scans it, then the first scans the answer QR. The app uses a WebRTC data channel without STUN/TURN relays, so the exchange is direct and DTLS-encrypted; pairing data is temporary and the QR should only be shown to a trusted register. Nearby sync merges shop-scoped POS records and queues received changes for normal Cloudflare sync. It does not provide device management or sync while the app is closed. When registers are apart, enable Cloudflare business sync for the same shop; changes remain local first and are uploaded in batches when online.

QR/barcode scanning during product entry is optional and runs locally in the app; it reads the code as a product SKU and does not use machine learning or upload camera images.

Storefront checkout creates tenant-scoped orders from the published catalogue; no delivery address or delivery fee is collected. The customer-facing published storefront posts the order to `POST /api/orders`, then starts hosted checkout through `POST /api/payments/paystack/initialize`; customer card details are entered only on Paystack. The storefront verifies the returned reference through `GET /api/payments/paystack/verify` and displays payment-pending/paid status from the server response. Website-builder preview disables payment. Orders require migrations `0008_storefront_orders.sql` and `0010_storefront_order_payments.sql`. Owners connect Paystack under **Studio → Payments**; that requires migration `0009_paystack_subaccounts.sql` and one Paystack **secret API key** stored as the `PAYSTACK_SECRET_KEY` Worker secret. The generic supported-bank directory is read-only and does not require shop-owner authorization; reading or changing a shop’s subaccount still requires owner authorization. There is no Paystack public key or separate webhook signing key to put in the app. Use a Paystack test secret for test transactions and switch the Worker secret to the live secret only for production. Bank and business details are sent to Paystack for setup but are not retained by E-Shop; D1 stores only the Paystack subaccount reference, connection state, bank name, and account last four digits. Subaccounts use zero E-Shop percentage share; transactions explicitly route Paystack processing fees to the shop’s subaccount, with no E-Shop transaction charge. Checkout initializes transactions server-side, uses Paystack-hosted authorization, and marks orders paid only after a matching Paystack verification or signed `charge.success` webhook. Payment requires positive KES orders and a connected subaccount; storefronts with another currency must not take payments until their catalog currency and prices are intentionally configured for KES. Stock is checked against the published catalogue when an order is received, but the endpoint does not reserve inventory atomically; do not treat the check as a guarantee against simultaneous orders.

Storefront visits can be sent anonymously to `POST /api/analytics/visit`; the owner reads tenant aggregates from `GET /api/analytics/visits`. The Worker records a hash of the random visitor identifier and coarse Cloudflare country/region metadata, not visitor IP addresses. It strips query strings and fragments from paths and retains only the referrer origin. Shared analytics requires the new D1 migration and is separate from each device's locally stored visit history.

To provision a Cloudflare environment:

1. Create the archive bucket: `npx wrangler r2 bucket create eshop-business-archive`
2. Apply the D1 schema, including migrations `0007_pos_sync_analytics.sql` through `0010_storefront_order_payments.sql`: `npm run cf:d1:migrate:remote`
3. Generate a VAPID key pair locally with Node:

   ```sh
   node -e "const c=require('node:crypto');const k=c.generateKeyPairSync('ec',{namedCurve:'prime256v1'});const p=k.publicKey.export({format:'jwk'});const s=k.privateKey.export({format:'jwk'});console.log(JSON.stringify({publicKey:Buffer.from([4,...Buffer.from(p.x,'base64url'),...Buffer.from(p.y,'base64url')]).toString('base64url'),privateKey:s.d}))"
   ```

4. Put the generated `publicKey` in `VAPID_PUBLIC_KEY` in `wrangler.jsonc`. Keep `privateKey` out of source control and add it as a Worker secret: `npx wrangler secret put VAPID_PRIVATE_KEY --config cloudflare/wrangler.jsonc`. `VAPID_SUBJECT` is a contact address and can be changed in the config.
5. Add the Paystack secret key as a Worker secret; never put it in app code or `wrangler.jsonc`: `npx wrangler secret put PAYSTACK_SECRET_KEY --config cloudflare/wrangler.jsonc`.
6. Set the Paystack webhook URL in the Paystack dashboard to `https://eshop-storefront.ryanrobin07-ek.workers.dev/api/payments/paystack/webhook` and enable the `charge.success` event.
7. Deploy the Worker and assets: `npm run cf:deploy`

Push is Web Push for supported HTTPS browsers. Visitors must separately grant notification permission; newsletter sign-up alone does not opt them into push. Broadcasts require the shop owner key and VAPID configuration. Expired subscriptions are removed, and send counts (not subscription endpoints) are archived in R2. Capacitor webviews that do not implement `PushManager` will report that push is unsupported.

If any provisioning step is skipped, the relevant API returns a configuration error; the local business data remains available.
