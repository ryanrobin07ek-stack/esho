# E-Shop

Web/PWA and Android wrapper for the supplied storefront. Uses native SQLite on Android and the community plugin's SQLite WebAssembly implementation persisted in IndexedDB for browser/PWA.

The app opens on a workspace launch screen: POS opens the local point-of-sale tools at `/pos`, Live Web opens the storefront at `/web`, and Web Builder opens the Studio at `/account`.

POS has its own SQLite-backed inventory, categories, checkout, receipts, credit and partial payments, invoices, expenses, till movements/close, tax and currency settings, business analytics, and timed/counted business instances. Overview reports pre-tax net sales from fully paid receipts separately from tax and payment collections, which can include partial or cross-period settlements. It includes revenue trends and period comparisons, a period profit-and-loss view and recorded-profit trend with qualified break-even estimate, best sellers versus fully costed gross earners, Pareto product contribution groups, category revenue/margin/mix, basket pairs, customer lifecycle and concentration, margin and recorded cost-change signals, stock cover and inventory value, dormant-stock exposure, overdue credit, payment-mix changes, calendar-normalized weekday and qualified complete-month segment patterns, robust large-receipt review prompts, data-quality coverage, and a saved monthly pre-tax net-sales goal with required daily pace and personal historical benchmarks. Priority alerts are severity-ranked and can be dismissed or snoozed; underlying signals are derived from local POS records, with minimum-history, cost, date, and attribution limitations called out. Category analytics use each product's current category. POS follows the E-Shop visual system but keeps its data separate from the online storefront catalog. Mobile-money payments can be recorded manually; incoming SMS and automatic M-Pesa matching/confirmation are not integrated.

In the Android POS app, **More → Settings → Nearby device sync** supports offline phone-to-phone sync over Bluetooth Classic. One phone taps **Receive over Bluetooth** and allows temporary device visibility; the other taps **Find a Bluetooth register**, selects the trusted phone, and accepts Android's pairing prompt if shown. Both phones must select the same shop in Studio. The app exchanges local POS snapshots and merges only records for that shop; snapshots can include receipt customer names and phone numbers. No Wi-Fi, internet, or Cloudflare connection is required.

For a phone-to-browser nearby live connection, keep both devices on the same Wi-Fi and online while pairing. The browser displays one QR; the phone scans it once, and the browser asks the operator to approve the phone before sending anything. Internet is used briefly to relay the WebRTC connection answer; the encrypted initial POS snapshots and subsequent changes transfer directly over Wi-Fi. While both registers stay open and connected, saved changes are pushed immediately and the Settings status shows the connected device and last update. The browser does not need a camera, and no second answer QR is required. Closing either register ends nearby live sync. Cloud backup remains available for changes while devices are not directly connected and checks for updates every five seconds while open.

The web register has **Use this shop's POS**, **Disconnect shop**, and **Reset browser POS data** controls above the register. After connecting an account or owner key with access to a shop, **Use this shop's POS** replaces only this browser's local POS records with that shop's cloud records and enables ongoing cloud sync. The other device can use a different login account as long as that account has access to the same shop. Disconnect turns off cloud sync on this browser but keeps its local POS records. Reset stops nearby sync and permanently deletes this browser's local POS database and saved shop connection after confirmation; it does not delete Cloudflare records or data on other devices.

Install dependencies with npm install. Run npm run dev for browser development; npm run build creates the PWA assets; npm run lint:inline checks the index.html application script for undefined names. Deploy over HTTPS to enable installation and offline shell caching.

For Android, install Android Studio and the Android SDK, then run: npm install; npx cap add android; npm run cap:sync; npx cap open android.

Normal Android builds use `https://rrobin.co.ke` as the local WebView hostname so Turnstile sees the same stable, allowlisted hostname on every installed app; allow `rrobin.co.ke` in the Turnstile widget once. To enable Android live reload, start `npm run dev -- --host 0.0.0.0`, set `$env:CAPACITOR_LIVE_RELOAD_URL = 'http://localhost:5173'`, run `adb reverse tcp:5173 tcp:5173`, sync, then build and install the debug app once. The installed app then loads from Vite; keep that server and reverse tunnel running and edit/reload the app without rebuilding or reinstalling for each change. Live reload replaces the stable app hostname, so Turnstile registration may not work in that mode. The live-reload URL is only embedded when this environment variable is set; leave it unset for normal builds.

Storefront collections are saved as JSON payloads in separate SQLite tables. POS records use relational SQLite tables in the same local database. Existing ESHOP_SQLITE_DB_V1 browser data is migrated on startup. Data remains on the device; there is no server sync or online payment integration.

Studio and POS product photos are compressed on-device to WebP (up to 1800 px and 1.5 MB) before being stored in the product's SQLite image list. The original selected file can be up to 5 MB. Uploaded photos remain available offline; publishing uploads compressed copies to the Cloudflare Worker, which stores them in the `media/<tenant>/` prefix of the configured `BUSINESS_ARCHIVE` R2 bucket and adds the public image URLs to the deployed catalog. External product-image URLs are also fetched and converted to WebP at no more than 800 px before upload; if an external image cannot be copied, publishing keeps its original URL and reports the fallback. Storefront product images load lazily with reserved dimensions. Image uploads must finish successfully before the catalog is published, except for external URLs retained as fallbacks.

## Publish multi-tenant shops to Cloudflare

The Cloudflare Worker serves the same `public/builder-storefront.html` for all shops. The apex `rrobin.co.ke` uses the `main` catalog, while each `shop-name.rrobin.co.ke` uses an independently stored tenant record in KV and an isolated catalog snapshot in D1. Create or sign in to an app account from **Account** on the home screen or in POS; that account is available throughout the app and is used when creating websites. Accounts use a username (no email or phone is requested) and a password hashed with PBKDF2-SHA-256 in the Worker; sessions are random, short-lived tokens stored by hash in KV. POS records remain local to the device and are not synced by account sign-in. Each shop receives a random 256-bit owner key; the app saves it in SQLite, and Cloudflare stores only its SHA-256 hash. Signing in issues additional shop-scoped keys, so a customer can restore access on another device without exposing the Cloudflare admin key. The app uses saved owner keys for private reads and publishing; when publishing a non-main website, its signed-in owner account can also authorize the update if the local shop key is unavailable. Studio **Shops & Tenants** switches the device's active editing catalog; shop drafts, inventory, and uploaded photos remain isolated in local SQLite. **Deploy storefront** in Products or Categories publishes only the currently selected tenant.

Before enabling registration, create a Cloudflare Turnstile widget for the app's public domains and configure the public site key and private secret on the Worker. Add `localhost` to the widget's allowed hostnames for the Android Capacitor WebView (the app runs at `https://localhost`); otherwise Turnstile returns error 110200. Set `TURNSTILE_SITE_KEY` in `cloudflare/wrangler.jsonc` (this is public), set `TURNSTILE_SECRET_KEY` with `npx wrangler secret put TURNSTILE_SECRET_KEY --config cloudflare/wrangler.jsonc`, apply the account schema with `npm run cf:d1:migrate:remote`, then deploy with `npm run cf:deploy`. Never put the Turnstile secret or `PUBLISH_TOKEN` in the app or source control. Registration and sign-in fail closed until Turnstile is configured.

An E-Shop app account is the owner identity for all websites created while signed in. Every website keeps its own catalog, store settings, orders, and analytics. Paystack is configured once under **Payments** in the E-Shop mobile app; the selected app-account default is resolved for checkout across all websites registered to that username. Changing the default changes the settlement account for those websites without sharing their shop data. New website setup does not request bank details. Paystack details are sent securely to Paystack for verification; E-Shop keeps only the subaccount reference and masked bank details, never the bank credentials in the browser or local SQLite. Paystack checkout in this integration currently requires KES: in the E-Shop mobile app, open **Payments**, set **Website currency** to Kenyan shillings, review prices because currency changes do not convert amounts, then publish the catalog from Web Studio.

The master `PUBLISH_TOKEN` can access all tenants and is required only for protected operations such as the main-shop setup and tenant administration. A one-time **Set up main shop key** action lets Studio exchange the master key for a main-shop-only key saved in local SQLite. Public storefront APIs expose product/catalog fields only; purchase cost is held in a separate private D1 payload and is returned only to the relevant shop owner. Rotate the master token after it has appeared in chat. The Worker serves only validated `media/<tenant>/` objects publicly; business-archive objects outside that prefix remain private. The app fingerprints local image data and caches each successful R2 upload per tenant, so unchanged images reuse their existing public URL on later publishes; a changed image is uploaded under its new fingerprint. Deploy the Worker after configuring its R2 bucket binding before publishing image-bearing catalogs.

The production D1 database, KV namespace, and Worker routes for the apex and wildcard are configured in `cloudflare/wrangler.jsonc`. On a newly created shop, the Worker uses `shop-name.rrobin.co.ke`.

For wildcard Worker routes to receive requests, Cloudflare DNS must have proxied apex and wildcard A records pointing to the reserved placeholder `192.0.2.1`:

| Type | Name | IPv4 | Proxy |
| --- | --- | --- | --- |
| A | `@` | `192.0.2.1` | Proxied |
| A | `*` | `192.0.2.1` | Proxied |

Keep existing explicit DNS records (for example `www`) unchanged; explicit records take precedence over the wildcard record. The Worker custom routes are already deployed, but DNS records require DNS-edit permission in the Cloudflare zone. If that permission is unavailable to Wrangler, add those two records in the Cloudflare dashboard.

Use `npm run cf:d1:migrate:remote` to apply pending production schema migrations, `npm run cf:deploy` to publish the Worker, and `npm run cf:dev` for local testing. Studio needs the Worker base URL and `PUBLISH_TOKEN`; catalog reads on each custom tenant subdomain are public, while tenant administration and catalog writes are authenticated. Wrangler sends `/`, `/api/*`, `/media/*`, `/themes/*`, and `/theme-skeletons/*` through the Worker; other static assets are served directly. Published filled storefront HTML is cached by hostname and catalog `updated_at`; the Worker serves only a tenant's saved filled output and fails closed if the output does not match the current catalog version.

## Shop-filled website themes

Theme templates and schemas are editor-only assets, not customer storefront pages. The picker and editor run the same fill engine with the shop's saved products, categories, and store details. A full catalog publish writes the filled HTML to the tenant's `published-sites/` prefix in `BUSINESS_ARCHIVE`; the storefront root serves that saved result, never the raw theme template. Raw theme HTML and direct skeleton navigation return 404. Publishing the filled output happens automatically after the catalog publish; no separate per-shop HTML upload is required. Deploy the app/Worker assets together so the editor-only template assets and Worker routes are current. Existing theme CSS, scripts, and media still need to be present under the shared `themes/<theme-id>/` R2 asset prefix.

Only Cira Atelier, Aura Luxe, and Kicks Vault currently have verified shop-data mappings and can be selected/published through this flow. Other generated theme skeletons are intentionally disabled until their product/category/store mappings and rendered output are verified; they do not fall back to demo content or an empty skeleton.

For local Worker development only, create `cloudflare/.dev.vars` with `DEV_SKIP_SHOP_CREATE_LIMIT=true` to test shop creation without the per-IP cap. Wrangler loads this file for `wrangler dev`; it is git-ignored and must not be copied into `wrangler.jsonc` or deployed settings. Production shop creation remains limited to five shops per IP per hour.

Build Your Web loads the complete workspace-root `index.html` as `public/builder-storefront.html` in a phone-height, internally scrollable iframe, preserving its HTML, CSS, scripts, navigation, categories, and full footer without phone/tablet/desktop preview modes. Live Web and the legacy Store Viewer route use the same full HTML storefront. Storefront links navigate inside that HTML app so product, collection, bag, and checkout screens keep the same catalog and cart instead of routing into a different storefront. Orders placed in embedded checkout are persisted to the host SQLite database. Its mobile layout is optimized for narrow screens, with touch-scrollable category/product rails and compact product, checkout, and footer layouts. At app startup, if SQLite Products and Categories are both empty, a hidden copy of the original HTML exports its catalog and the app imports it once using existing SQLite record formats and linked category IDs. This makes the products and categories immediately available in the Studio modules; existing app catalog records are never overwritten by the import. The host also passes its SQLite products, categories, and store settings into the visible preview. Product/category creation, edits, deletion, duplication, and stock updates made in the embedded catalog are written through the host SQLite engine and flushed before success is reported. Embedded mode uses a separate preview storage key and does not seed demo catalog records, preventing preview-only state from overwriting or migrating the host catalog. On first launch after this integration, existing website details, custom pages, hero-slide records, and stale legacy HTML browser state are reset; Products, Categories, and POS records are not cleared. The SQLite bridge ignores the standalone preview's legacy storage key during later imports, so its sample catalog cannot overwrite the app catalog. The separate Pages manager remains SQLite-backed.

Run `npm test` for the POS and Cloudflare tenant/catalog tests, or `npm run test:pos` for the local POS checkout, payment, invoice, and business-instance workflows.
