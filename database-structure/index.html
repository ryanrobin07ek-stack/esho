Craft app database map

A map of where the app keeps shop, product, inventory, sales, website, customer, and account data—and how those pieces connect.

Important: “Main Store” in the app is not the website tenant named main. The in-app Main Store is the merchant’s local shop workspace and POS data. The Cloudflare tenant main is a separate web/API identity. A shop such as Chapa has its own tenant-isolated catalogue, inventory, orders, and storefront activity.

1 · In-app shop database

SQLite database name: eshop. These app tables store each row as a JSON payload.

Shop identity & catalogue

storecategoriesproductspageshero_slides

Each table: row_id primary key, payload JSON text. Holds shop settings, product/category data, editable pages, and homepage slides.

Commerce & customer app data

inventoryfavoritescart_itemsorderscustomer_pointspayment_methodsmain_store_inventory

Each table uses row_id and JSON payload. main_store_inventory is a tenant-scoped local cache of POS/Web/Reserved allocations; Cloudflare D1 is the online authority.

App activity & content settings

analyticsweb_visitsweb_eventsnewsletter_subscribersbooking_holds

Each table uses row_id and JSON payload. Local records are not automatically identical to tenant-wide online activity.

Workspace / Studio records

planstenant_catalogswebsite_themesstudio_settings

Each table uses row_id and JSON payload. Stores local plans, shop catalogs cached on-device, theme library records, and Studio configuration.

Main Store, in plain language: Split shop is the explicit allocation screen. Products stay in their original channel until selected; a product deliberately shared between POS and Web has one master quantity divided into POS, Web, and Reserved units. The cloud allocation is tenant-scoped and keyed by SKU.

2 · POS database inside the app

These are additional relational SQLite tables created by the POS module.

Products & configuration

pos_categoriespos_productspos_settings

pos_products: id, name, category_id → pos_categories.id, price_cents, buying_price_cents, stock_count, sku, barcode, image_uri, expiry_date, image_embedding, low_stock_threshold, active, created_at. pos_categories: id, name. pos_settings: key, value.

POS sales

pos_salespos_sale_itemspos_sale_payments

pos_sales: id, receipt_number, subtotal/tax/discount/total cents, currency, payment_method, paid, customer_name/phone, due_date, payment_status, amount_paid_cents, created_at. Items reference sale_id and record product/name/quantity/prices/cost. Payments reference sale_id and record method, amount, fee, status, M-Pesa reference, sender, time.

Expenses, invoices & cash

pos_expensespos_invoicespos_invoice_itemspos_cash_movementspos_till_closes

Expenses have date/category/label/amount/currency/method/note and sync_key. Invoice headers store customer, due date, notes and totals; invoice items reference invoice_id. Cash movements and till-close records store amounts and reconciliation.

POS devices & sync queues

pos_instancespos_business_recordspos_cloud_outboxpos_inventory_queue

Instances track timed/counting sessions. Business records are keyed by tenant_id + entity + record_id and contain JSON payload/revision/deleted flags. Outbox queues records to Cloudflare. Inventory queue tracks stock connect/sale events and sync status/errors.

Connected inventory mirror

shared_inventoryshared_inventory_eventsshared_inventory_event_items

shared_inventory is keyed by tenant_id + SKU and stores current stock. Event headers and line items record stock changes. Database triggers reject sales that exceed stock and deduct the quantity. This is distinct from the product’s saved catalogue stock field.

3 · Cloudflare D1 database

Configured D1 database: eshop-catalog. Shop-facing data is scoped by tenant_id unless account-global.

Shop catalogue

catalog_snapshots

tenant_id primary key; payload JSON (published products/categories/store/pages, including each product’s saved stock); admin_payload private JSON; updated_at. This is the snapshot the hold handler currently reads.

Accounts & shop ownership

accountsaccount_tenantsaccount_google_identities

accounts: username, password_salt/hash, created_at, email. account_tenants: username → accounts.username, tenant_id unique. account_google_identities: google_sub, unique username → accounts.username, email, created_at.

Main Store allocations & POS stock

main_store_inventoryinventory_stockinventory_eventsinventory_event_items

main_store_inventory: tenant_id + SKU key; channel ownership, enabled flags, master_stock, pos_stock, web_stock, reserved_stock, updated_at. A CHECK enforces master = POS + Web + Reserved. POS events and stock sync update this allocation; triggers prevent POS from using stock outside its allocation. inventory_stock remains the POS event mirror.

POS sync & branches

pos_sync_changesbusiness_branches

pos_sync_changes: revision, tenant_id, change_id, device_id, entity, record_id, JSON payload, deleted, changed_at. Unique (tenant_id, change_id). business_branches: tenant_id, store_id, store_name, snapshot_id, r2_key, updated_at.

Online orders & activity

storefront_ordersstorefront_visitsstorefront_product_interest

storefront_orders: tenant_id/order_number, idempotency_key, status, customer/contact/shipping, currency, totals in cents, items_json, payment_status/reference/authorization_url/paid_at, timestamps. storefront_visits: id, tenant_id, visitor_hash, path/referrer/device/country/region, created_at. storefront_product_interest: tenant_id + visitor_hash + product_id, cart_quantity, wishlist_active, timestamps.

Holds, web stock deductions & newsletter

storefront_hold_requestsstorefront_inventory_deductionsnewsletter_subscribers

Approved holds reserve against available Web stock. Paid order deductions are unique by tenant + order + SKU; triggers check Web allocation and active holds before decreasing both web_stock and master_stock. Subscribers: id, tenant_id, email/name/status, confirmation/unsubscribe tokens, consent/confirmation/unsubscribe timestamps.

Payment configuration

paystack_subaccountspaystack_owner_defaults

paystack_subaccounts: tenant_id, subaccount_code, status, bank_name, account_last4, timestamps. paystack_owner_defaults: owner_username, source_tenant_id, timestamps.

Nearby pairing & notifications

nearby_pairingspush_subscriptions

nearby_pairings: id, tenant_id, host/guest token hashes, offer/answer SDP, created_at, expires_at. push_subscriptions: tenant_id, endpoint_hash, endpoint, p256dh, auth, created_at.

4 · Cloudflare KV and R2

These stores are not relational tables.

KV namespace · tenant and pointer records

tenant:<tenantId> stores tenant metadata and owner-token hashes. published-theme:<tenantId> points to the current filled theme object and catalogue version. Other keys support sign-in sessions, password recovery, Google sign-in state, verification, rate limits, and short-lived caches.

R2 bucket · files and snapshots

published-sites/<tenantId>/<themeId>/<version>.html stores published storefronts. media/<tenantId>/... stores shop media. Branch archives and push archives are stored as separate objects. The KV published-theme pointer identifies the active published HTML.

5 · How the data moves

These connections matter when stock or storefront activity appears inconsistent.

App product recordProduct name, price, images, SKU and stock are saved in local app SQLite.
Publish websiteThe app sends a copy of products/categories/settings to D1 catalog_snapshots, then stores filled HTML in R2.
Customer storefrontThe published theme renders the catalogue snapshot for that hostname’s tenant.
Main Store allocationThe Split shop screen saves tenant + SKU channel membership and exact POS/Web/Reserved quantities to D1 main_store_inventory.
POS stock changesPOS sales/restocks change inventory_stock; D1 triggers mirror that difference into the POS and master allocation while preserving Web and Reserved stock.
What website readsThe catalogue API returns web_stock for explicitly allocated products and zero for products disabled for Web. Products without an allocation keep the published catalogue stock.
Web ordersOrder requests check Web allocation and active holds. On successful payment, a unique deduction row and triggers decrease Web and master quantities once.
Orders & activityOnline orders, visits, cart/wishlist interest, holds, and newsletter signups are stored in separate tenant-scoped D1 tables.
Important: products without a saved allocation continue using their existing channel stock. Allocations are not backfilled or guessed; the owner must explicitly select products and confirm any shared product’s master quantity.
