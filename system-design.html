01 / NOW

Executive summary

The design target is an app that remains useful without a network and synchronizes with D1 when connected.

Local truth

Device SQLite

The app stores Studio records in the SQLite snapshot database. POS tables—including products, sales, queue, and shared inventory—are also created through the same ShopSQLite native SQLite connection.

Remote copy

Cloudflare D1

D1 holds the published catalog snapshots and, after the migration is applied, the online shared-stock mirror and idempotency event ledger. It is reached through the Worker API, not directly by the handset.

Offline rule

Do local work locally

POS receipts, stock deductions, local browsing from a previously cached catalog, and local edits should not require a connection. Publishing, account services, and public internet checkout do.

Important distinction. “One SQLite” means the app’s Studio product mirror and POS shared-stock ledger run on-device through the same SQLite engine. The published internet storefront runs on a customer’s browser and cannot read the owner’s private phone database. D1 is the bridge between separate devices and public browsers when online.

03 / APP

App runtime and surfaces

A single client application presents several operational surfaces over the same local persistence layer.

Android shell

Capacitor hosts the built web app in a WebView. src/bootstrap.js initializes SQLite, creates the POS application, waits for readiness, and connects native back-button handling. The Android project packages the current www assets.

  • Native SQLite plugin is used on Android.
  • The app does not need a network just to open local POS and Studio data.
  • The built APK is an installable artifact; this design page is not an app route.

Browser / PWA shell

Vite builds the same app sources for browsers. In web mode src/sqlite.js initializes jeep-sqlite and saves the database to browser storage.

  • Browser data belongs to that browser profile and device.
  • Native and browser databases are not magically shared with one another.
  • The public storefront is a separate visitor context and relies on its own cache plus Worker/D1 requests.

Main app domains

POS

Cart, products, receipt checkout, sales history, payment records, invoices, expenses, business instances, reporting.

Studio

Shop accounts, website selection, product/catalog editing, stock management, themes, pages, publishing, tenant management.

Storefront

Public catalog rendering, search, product pages, cart, checkout, order confirmation. Online publication lives behind the Worker.

Cloud services

Account/session endpoints, tenant ownership, catalog publishing/loading, shared stock setup, and online sale recording.

04 / DB

SQLite: the local working database

The local database is both application storage and the immediate stock authority for linked POS and Studio products.

POS-specific tables are created by initializePosDatabase() over window.ShopSQLite. Studio tables are JSON-payload rows managed by the existing SQLite snapshot engine. Shared inventory is normalized SQL; it is not itself a separate SQLite file.

Persistence and transactions

src/sqlite.js opens the database named eshop, serializes asynchronous database work through an operation queue, and exposes query/run/execute/executeSet/save/flush. Multi-statement POS checkout uses a SQL transaction; web mode commits through the jeep-sqlite store.

SKU is the cross-catalog key

A website product and POS product represent the same sellable stock only when they share the exact SKU for the same tenant. Product names are editable and may repeat; names are not a reliable identity. The connection screen only synchronizes matching SKU values.

05 / STOCK

Shared inventory and stock invariants

One local stock balance is decremented once per recorded sale; mirrored UI product rows are then refreshed from that balance.

Core invariant: for each (tenant_id, sku), the local shared ledger is the immediate stock authority on the app device. A linked POS checkout or app storefront checkout records a unique event and decrements that ledger in a transaction. Product and inventory views are mirrors of the ledger, not separate stock pools.
1 · Identify

Tenant + SKU

Every stock row is scoped to a website/shop ID and product SKU, so two tenants can use the same SKU without colliding.

2 · Validate

Quantity + stock

Quantity is a positive whole number. SQLite triggers reject a linked sale if the shared balance is insufficient.

3 · Deduct

Atomic local event

A unique event header and its sale lines are committed together; triggers deduct the shared balance.

4 · Mirror

Refresh product views

POS stock count and Studio product/inventory views reflect the shared quantity for the matching SKU.

5 · Replicate

Queue for D1

Event or stock setup is queued locally. When online, Worker receives it and D1 becomes the remote mirror.

Connection bootstrap

  1. Choose a shop/website in POS inventory.
  2. Set the exact matching SKU on each POS and website product that should share stock.
  3. Choose the starting stock source: “Use POS stock for website” or “Load website stock into POS.”
  4. App writes the linked balances into local shared_inventory and marks them shared in the local catalog.
  5. The initial replacement is queued and sent to D1 when online. Reinitializing an already connected link requires confirmation because it replaces quantities.

Unlinked products remain independent

Products without a shared tenant/SKU connection keep their existing local POS or Studio stock behavior. The shared ledger does not guess a match by name, and an unmatched row should never silently merge.

A stock edit or restock in POS/Studio for a linked SKU should update the same SQLite stock record and enqueue a stock replacement for remote synchronization.

06 / OFFLINE

Offline-first behavior

Connectivity is a capability boundary, not a prerequisite for using the local business app.

Offline concurrency limit. The phone can enforce stock against its own saved ledger while offline. A separate public storefront or another device cannot see those unsent sales. If both sell the last unit before synchronization, D1 may reject the later-arriving sale. The app should preserve the receipt, show a sync conflict clearly, and require stock reconciliation; it cannot retroactively guarantee global no-oversell across disconnected devices.

Device cache rule

A public storefront fetches its catalog from /api/catalog and saves a hostname-scoped browser cache. If that fetch fails and a valid saved catalog exists, it can render that catalog with an offline notice. A first visit with no cache cannot invent the remote catalog. Public checkout remains an online operation, even when the catalog can be browsed offline.

07 / FLOWS

End-to-end data flows

The decision points that matter: local-first checkout, retry-safe delivery, remote checkout, and catalog publication.

A. POS sale on the owner device

Operator submits cart.POS validates items, prices, quantities, payment inputs, current product records, and stock.
SQLite transaction begins.Receipt header and receipt lines are inserted; POS product counts are reduced. If linked, the event ledger and queue record are inserted too.
Shared stock trigger runs.For each linked SKU, the local trigger checks that enough shared stock remains and decrements it. If not, the whole transaction fails.
Receipt is committed locally.The checkout remains complete even if the phone has no internet; local customer/receipt data remains on the device.
Sync worker attempts delivery.When online, the queue sends the event to POST /api/inventory/sale. The event ID makes a retry safe after a lost response.
D1 response reconciles stock.Once accepted, app can read remote shared stock and refresh SQLite mirrors. Insufficient remote stock is a conflict, not a reason to erase the local receipt.

B. Public storefront sale

Customer submits

Browser has an online connection and submits cart/order details.

Identify shared lines

Only products marked shared with a valid SKU affect shared stock.

Worker sale API

POST /api/inventory/sale validates event ID and items.

D1 atomic deduction

Event/lines and stock changes are committed as one batch.

Confirm order

On rejection, customer sees an error and order is not shown as successful.

Public visitor browser and owner phone are not a single physical SQLite database. The public sale changes D1 first; the owner app later reads D1 and mirrors its current stock into local SQLite.

C. Lost reply, duplicate retry, or reconnect

local event ID = stable receipt/event key
        │
        ├─ request reaches Worker and D1 commits
        │    └─ response is lost → phone still marks event pending
        │
        └─ phone retries the SAME event ID
             └─ Worker sees existing (tenant_id, event_id)
                  └─ returns success + duplicate=true (no second deduction)

on app reconnect:
  1) read pending local queue rows in creation order
  2) POST connection snapshot or sale event
  3) mark successful rows synced; keep failures with explicit error
  4) GET D1 shared-stock rows
  5) update local shared ledger and product/inventory mirrors

D. Publish an edited catalog

Studio reads its selected tenant draft from SQLite, assembles public and private catalog fields, and sends an authenticated catalog update to the Worker. Worker validates and cleans fields, saves a public snapshot and owner/admin snapshot in D1, and returns publish metadata. This operation requires internet. The phone still retains its local editable catalog if publishing fails.

08 / CLOUD

Worker API and D1 model

Cloudflare provides a cross-device mirror and public service boundary; it does not replace local app persistence.

Worker responsibilities

  • Route catalog, account, tenant, and inventory API requests.
  • Validate request shapes, tenant identifiers, SKUs, event IDs, quantities, and method permissions.
  • Authenticate owner actions using shop credentials; avoid handing a master publish secret to storefront visitors.
  • Store or retrieve D1 catalog data and shared-stock state.
  • Return explicit HTTP errors for missing authorization, insufficient stock, invalid payloads, and unavailable services.

D1 tables in migration 0005

  • inventory_stock: primary key is (tenant_id, sku), with nonnegative stock.
  • inventory_events: primary key is (tenant_id, event_id) for idempotency.
  • inventory_event_items: event SKU quantities, foreign-keyed to event and stock records.
  • Before-insert trigger rejects a line if there is not enough stock; after-insert trigger deducts it.
  • Catalog snapshots keep public payload separate from protected admin payload.

09 / TRUST

Security, privacy, and trust boundaries

The most important architectural rule is that public browsers, owner app storage, Worker secrets, and D1 are different trust zones.

Owner device

Local business data is stored in SQLite on the device/browser profile. Device lock, Android backup policy, physical access, and account-session handling are part of the data-security model.

Public storefront

Visitors may read the public catalog and submit checkout requests. They must not receive owner tokens, private catalog fields, account session secrets, or the Cloudflare administrator key.

Worker and D1

Worker is the API boundary. Validate tenant scope and request contents server-side; do not rely on browser-side validation to secure a stock update. D1 writes should be transactional and idempotent.

Design requirements to preserve

  • Never include owner/master credentials in public catalog payloads or visitor HTML.
  • Use parameterized D1 queries; never form SQL by concatenating a visitor-provided SKU or tenant value.
  • Scope every event and stock row by tenant.
  • Use stable event IDs to prevent duplicate deduction after timeout/retry.
  • Validate numeric bounds and item count before batching.
  • Keep private admin catalog reads behind owner authorization.
  • Show sync failures as failures; do not silently mark queued changes delivered.

Build, migration, and deployment workflow

Keep local app delivery distinct from remote cloud activation.

npm run build
npm run cap:sync

# Validate D1 SQL locally (does not alter remote production)
npm run cf:d1:migrate:local

The app uses Node test files under tests/; Vite produces web assets under www/; Capacitor copies those assets into Android.

Remote activation (operator-controlled)

# Explicit production changes:
npm run cf:d1:migrate:remote
npm run cf:deploy

# Then verify:
# 1. Worker reports healthy
# 2. owner-authenticated inventory/connect works
# 3. D1 GET stock matches owner app
# 4. test sale changes stock exactly once

Remote migration and deploy are production-impacting operations. Do not run them without the project owner’s explicit go-ahead and correct Cloudflare credentials/config.

13 / TERMS

Glossary and design decisions

Shared language for product, engineering, and operations.

Glossary

  • SQLite: a relational database stored with the app on a device/browser.
  • D1: Cloudflare’s hosted SQLite-compatible database, reachable by the Worker.
  • Worker: server-side JavaScript endpoint that mediates internet requests.
  • Tenant: one shop/website namespace; IDs prevent data mixing across shops.
  • SKU: stable product identifier shared between POS and website catalog rows.
  • Idempotency: repeating one event ID has the same effect as applying it once.
  • Mirror: a display/cache copy of the canonical shared stock balance.
  • Queue: durable local list of changes that still need delivery to D1.
  • Reconciliation: resolve local-vs-remote stock differences after disconnected activity.

Decision record

  • POS is allowed to operate offline and records receipts locally.
  • Offline POS sales are queued and synchronized when a network is available.
  • Website and POS linking uses exact SKU, not product name similarity.
  • Initial shared stock source is explicit and user-selected.
  • Cloud-only actions should say they need internet; unrelated local app screens should remain usable.
  • Global no-oversell cannot be guaranteed while multiple sellers are disconnected.
